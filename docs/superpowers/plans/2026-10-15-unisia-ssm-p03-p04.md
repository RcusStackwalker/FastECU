# Unisia SSM P03/P04 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Share the identical framed-send and single-receive operations used by the Unisia K-Line and bootmode programming executors without changing either family's wire behavior.

**Architecture:** Add two explicit operations to the existing package-owned `m32r_ssm_exchange` module. Its existing combined optional exchange has an additional after-write cancellation checkpoint and remains unchanged. Unisia executors retain their separate send/read call sites, sessions, parsers, timeouts, polling, and programming policies.

**Tech Stack:** C++23, portable byte spans/vectors, injected K-Line transport and cancellation ports, GoogleTest/Google Mock, Bazel, Gazelle, prek.

**Spec:** P03/P04 in the [production clone inventory](../specs/2026-10-14-flash-duplication-triage.md), the Unisia responsibility in the [confirmed investigation](../specs/2026-10-14-flash-duplication-investigation.md#module-responsibilities), and the [sharing contract](../../design-notes.md#share-only-proven-protocol-equivalence).

## Global Constraints

- “Keep family executors as orchestration owners.”
- “Preserve current behavior during extraction; propose evidence-backed corrections separately with a reproducing test and qualification divergence note”.
- “Retain independent family transcript expectations; do not generate expected wire bytes through the extracted implementation.”
- “Qualification evidence and hardware status do not improve through refactoring.”
- Scope is P03/P04 only. No changes to bootmode kernel upload, read windows, erase loops, programming voltage, cleanup precedence, block acknowledgements, final-block silence, retry counts, baud rates, or delays.
- No Qt, owned threads, filesystem I/O, new ErrorKind, dependencies, behavioral switches, or widened visibility. Production Result/Status checks use `.has_value()`.
- Send checks cancellation only before writing. Receive performs exactly one read, propagates its error first, then checks cancellation. Do not insert a pre-read or after-write cancellation check.
- Preserve AddHeader behavior, including one-byte length wrapping; compare the write count against the full request size. Do not add payload validation.
- Keep `ExchangeM32rSsmOptional` and `M32rSsmPayloadHasPrefix` behavior and existing consumers unchanged.

## Review Focus

- Cancellation raised during a successful send must not change that send's successful result (Task 1).
- Receive invoked with cancellation already requested still calls the transport once; transport errors win over cancellation (Task 1).
- An absent reply and a present empty reply remain distinct, and malformed bytes pass through unchanged (Task 1).
- Alternate tester/target IDs and payload lengths 0/256 preserve framing and full-size write checks (Task 1).
- Family polling and cleanup paths retain their exact operation ordering, timeouts, and error precedence (Task 2).

### Boundary choice

Use the existing M32R SSM module with separate entry points: it already owns framing and injected transport interactions in this package. A new Unisia-only module would also fit the responsibility but duplicate module plumbing. Reusing the combined optional exchange is unsuitable: Unisia sends and receives separately during polling, and the existing exchange adds an after-write cancellation checkpoint. Do not generalize this into configurable checkpoint policy or refactor the combined exchange in this change.
