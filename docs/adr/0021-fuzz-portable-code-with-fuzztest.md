# ADR 0021: Fuzz Portable Code with FuzzTest under Clang Only

## Status

Accepted and implemented by `bazel/fuzz.bazelrc`, the `_fuzz_test` branch of
`fastecu_portable_gtest`, and the PR workflow's sanitizer job.

## Context

The portable code parses input FastECU does not control: ECU replies on the
wire, ROM files, definition XML, conversion expressions and terminal scripts.
Example-based tests show those parsers handle the inputs someone thought of; a
malformed reply that reads past a span or a definition that overflows an index
is found only on a bench or by a user. Every C++ suite is GoogleTest, tests are
package-owned ([ADR 0008](0008-use-package-owned-mocks.md)), and Gazelle
generates the test targets
([ADR 0017](0017-generate-bazel-targets-with-gazelle.md)).

## Decision

- Harnesses are FuzzTest `FUZZ_TEST` properties in `<unit>_fuzz_test.cpp`,
  beside the unit, generated by Gazelle as `fastecu_portable_gtest` targets.
  The `_fuzz_test` name suffix selects FuzzTest's main, a `fuzz` tag, and a
  `target_compatible_with` gate, because `gazelle_cc` cannot choose a rule
  kind by file suffix.
- Scope is portable code: `src/algorithms` and `src/backend`.
- Harnesses build only under `--config=asan` (ASan + UBSan, FuzzTest's
  unit-test mode) or `--config=fuzztest` (coverage-guided fuzzing), both of
  which require Clang. Every other build, including the release jobs on all
  three platforms and the Android cross-compile, skips the targets and never
  fetches FuzzTest's dependency graph. MSVC never builds them.
- The PR gate is a Linux job on the clang-tidy job's pinned LLVM that runs all
  portable tests and harnesses under `--config=asan`, replaying every
  committed seed. Coverage-guided runs happen outside the PR gate.
- Seeds are synthetic files of at most 4 KiB under `testdata/fuzz/`; stock ROM
  bytes and bench reads are never committed.

## Alternatives

- `rules_fuzzing` with libFuzzer: a separate `cc_fuzz_test` rule per harness
  with raw `LLVMFuzzerTestOneInput` byte entry points, outside GoogleTest and
  Gazelle's generated test kind. Its generated regression targets duplicate
  what FuzzTest's unit-test mode already provides.
- Hand-written libFuzzer binaries: the same, plus Bazel rules we would own.
- `FUZZ_TEST` inside the existing `*_test.cpp`: FuzzTest would enter every
  test binary, including the Windows ones it cannot build.
- Running harnesses in the main macOS job with Apple clang: FuzzTest supports
  macOS only experimentally, so a gate there would depend on it.

## Consequences

- `MODULE.bazel` carries FuzzTest as a dev dependency plus root
  `single_version_override`s for modules in its graph that predate Bazel 9.
  A FuzzTest bump is the time to try dropping them.
- The root module resolves FuzzTest's whole graph (protobuf, flatbuffers,
  riegeli, abseil) on every build, though it fetches it only for the fuzz
  configs.
- Fuzz harnesses are not yet analyzed by clang-tidy; see the
  [technical debt](../tech-debt.md#p2-analyze-fuzz-harnesses-with-clang-tidy).
- Conventions for writing harnesses and seeds are in the
  [coding style guide](../coding-style.md#tests).
